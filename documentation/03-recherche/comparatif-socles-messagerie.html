Choix proposé

Je recommande Matrix avec Synapse et un connecteur local de confiance par agent. Element peut servir d’interface humaine facultative ; il n’est pas le moteur de communication des agents. XMTP constitue la seconde combinaison à prototyper si MLS et les identités cryptographiques priment sur la maturité et la fédération.

L’équipe, les volumes et le budget ne sont pas connus. Aucune exploration ne peut garantir avoir couvert toutes les technologies existantes ; les principales familles pertinentes sont comparées ici.

Element est-il le meilleur choix ?

Matrix est le protocole ; Synapse est un serveur ; Element est une famille de clients et de distributions. Element X s’appuie sur le Matrix Rust SDK. Pour des agents, utiliser le SDK et les API plutôt qu’automatiser l’interface Element. Element — clients ; Matrix Rust SDK — bibliothèque clients et bots.

Le SDK fournit notamment des fonctions de chiffrement et de synchronisation et vise aussi les bots. Le daemon local Polytalk restera nécessaire pour traduire les messages en événements adaptés à chaque agent. Matrix Rust SDK — bibliothèque clients et bots.

Choix proposé : Synapse auto-hébergé avec PostgreSQL pour l’évaluation. Examiner licences des composants et support avant le déploiement commercial ; la documentation d’Element présente ESS Community pour l’évaluation et les usages non professionnels. Ne pas confondre ce positionnement avec une conclusion juridique sur l’ensemble de Matrix. ESS Pro est une option de support à chiffrer, pas un achat décidé. Element Server Suite Community — périmètre annoncé ; Synapse — dépôt maintenu et licence.

Chiffrement et identité

Le chiffrement Matrix standard repose sur Olm/Megolm ; il ne faut pas le présenter comme MLS. Matrix — Olm et Megolm. Le contenu est déchiffré dans le daemon autorisé. Les identifiants, membres, informations d’état et flux réseau ne deviennent pas tous secrets. Les politiques de vérification des appareils et de rotation sont obligatoires pour le mode privé.

L’identifiant stable Polytalk doit être relié de manière vérifiable à l’utilisateur Matrix et aux appareils autorisés. Un identifiant Matrix seul n’est pas une preuve cryptographique de type wallet. Ne pas ajouter de blockchain sans besoin démontré. Les sauvegardes de clés, récupération et arrivée d’un appareil demandent une politique explicite.

Une passerelle centrale qui lit puis rechiffre devient une extrémité de confiance. Ne pas la présenter comme un simple relais E2EE. Éviter une pile Matrix + SLIM + deux mécanismes de groupe sur chaque message : choisir un chemin de livraison par conversation.

Seconde combinaison : XMTP

XMTP décrit une destination stable de type inbox, des identités et des installations avec leurs propres clés. Cela correspond bien à l’intention initiale du projet. XMTP — modèle d’identité. Son socle utilise MLS pour les conversations, mais conserve des métadonnées observables. XMTP — présentation et garanties annoncées.

Point bloquant découvert : le quickstart actuel propose un SDK 8.0.0-rc2 ; il ne faut pas le traiter comme une version stable validée pour Polytalk. XMTP — quickstart et versions recommandées. La documentation de migration indique que les contacts doivent rejoindre le même réseau auto-hébergé pour recréer des conversations actives ; importer l’historique ne suffit pas. XMTP — migration, réseaux auto-hébergés et rattrapage.

Prototyper seulement sur un couple backend/SDK épinglé. Vérifier identité non financière, dépendances de démarrage, fonctionnement sans Internet, stockage, licences et limites. L’existence d’un guide auto-hébergé ne démontre pas une fédération universelle entre réseaux isolés.

Éditions Internet et intranet autonome

En ligne : service accessible sur Internet avec TLS, gestion des comptes et fédération contrôlée si retenue. Aucun contenu privé dans les services push ou journaux.

Intranet hors Internet : serveur, base, annuaire, authentification, certificats et maintenance disponibles localement. Déployer un paquet versionné avec dépendances et images préparées ; aucun téléchargement de CDN ni service cloud obligatoire à l’exécution. La fédération extérieure est désactivée ; une fédération interne peut être qualifiée séparément.

Les postes restent connectés au réseau local. Si tous les réseaux sont absents, seule une file locale est possible et l’échange attend une reconnexion. Un intranet isolé ne permet pas d’appeler les modèles cloud : prévoir agents locaux ou fournisseurs internes. Aucun tunnel sortant automatique.

Décision et conditions de révision

Retenir Matrix comme socle de référence du MVP, garder XMTP comme alternative et réserver SLIM/MLS à une extension spécialisée. L’ADR-004 antérieure devient une piste conditionnelle et non une obligation de transport général. La progression API/MCP → A2A → validation SLIM/MLS est conservée, avec Matrix préparé au socle et sa réception événementielle dès la première étape.

Revoir ce choix si l’exigence devient « MLS obligatoire sur chaque conversation », si les volumes mesurés le justifient ou si le PoC Matrix échoue à l’intranet autonome, aux notifications ou à la récupération des clés. Aucun coût ou SLA n’est inventé.

Glossaire

API
Interface d’accès programmatique aux fonctions de Polytalk.
MCP
Model Context Protocol : accès d’un agent à des outils et ressources.
A2A
Agent2Agent : protocole d’interaction entre agents indépendants.
SLIM
Secure Low-Latency Interactive Messaging : infrastructure de transport et de sessions.
SLIMRPC
Binding RPC sur SLIM ; l’intégration A2A correspondante reste expérimentale.
MLS
Messaging Layer Security : protocole de chiffrement de groupe utilisable aussi pour deux clients.
Binding
Association des opérations d’un protocole à un transport et à une représentation sur le réseau.
Protobuf
Format de sérialisation structuré utilisé par le binding SLIMRPC.
AAD
Additional Authenticated Data : données liées cryptographiquement au message mais non chiffrées.
Epoch
Version de l’état cryptographique d’un groupe MLS.
KeyPackage
Matériel public signé destiné à l’ajout d’un client MLS ; aucune clé privée ne doit être publiée.
Agent Card
Description des capacités et interfaces d’un agent ; distincte de la carte de contact cryptographique Polytalk.
Composant local de confiance
Processus sous le contrôle du propriétaire de l’agent, chargé des clés et du chiffrement.
PoC
Prototype destiné à vérifier la faisabilité ; il ne prouve pas à lui seul l’aptitude à la production.
ADR
Décision d’architecture datée, motivée et accompagnée de conséquences.
TLS / mTLS
Protection des connexions réseau ; mTLS ajoute l’authentification mutuelle. Ces connexions ne remplacent pas MLS.
Matrix
Protocole de messagerie et synchronisation fédérée.
Element
Clients et solutions autour de Matrix ; ni le protocole ni le moteur d’un agent.
Synapse
Implémentation de serveur Matrix auto-hébergeable.
XMTP
Infrastructure de messagerie avec identités cryptographiques et chiffrement MLS.
Daemon local
Processus persistant autorisé, près de l’agent, qui synchronise et signale les messages.
Hors ligne intranet
Serveur et clients connectés au réseau local, sans dépendance à Internet ; distinct d’un ordinateur sans aucune connexion réseau.
Curseur
Repère de synchronisation persisté pour reprendre la lecture des événements.
Idempotence
Gestion permettant de recevoir plusieurs fois un événement sans répéter son effet applicatif.
