Choisir ses moyens de connexion

Passkeys, clés physiques et application TOTP sont des choix individuels. Aucun facteur n’est ajouté automatiquement lors de l’inscription. Le nom civil, l’e-mail et le téléphone ne sont pas nécessaires : le pseudo peut servir de nom affiché.

Implémentation serveur et interface ajoutées. Les essais sur matériel réel et la qualification visuelle restent distincts des tests cryptographiques et HTTP. Ce document ne déclare pas l’ensemble de PolyTalk prêt pour la production.

1. Choix et parcours

Inscription ouverte par défaut : aucun code d’invitation à saisir. L’administrateur peut activer le mode sur invitation pour une installation privée ; le champ devient alors nécessaire uniquement dans ce mode. Les comptes existants restent inchangés.

Les sessions déjà ouvertes ne sont pas révoquées silencieusement quand la 2FA est activée. La phrase du coffre de chaque appareil reste distincte des méthodes d’authentification du compte.

2. TOTP et dix codes de secours

  1. Confirmer le mot de passe actuel.
  2. Scanner le QR local dans une application TOTP ou copier manuellement la clé de configuration.
  3. Saisir un premier code à six chiffres pour prouver que l’application est configurée.
  4. Conserver les dix codes de secours affichés, éventuellement dans un fichier personnel à imprimer.

Profil RFC 6238 : HMAC-SHA1, six chiffres, période de trente secondes et tolérance d’un pas temporel. Un pas déjà accepté ne peut pas être réutilisé. Les secrets TOTP sont chiffrés par AES-256-GCM avec liaison au compte ; la clé serveur est dérivée de POLICY_SECRET avec séparation de domaine. Conserver ce secret avec les sauvegardes privées du serveur : le changer sans migration rendrait ces facteurs illisibles.

Chaque code de secours contient 128 bits aléatoires et seul son condensat SHA-256 est conservé. Sa consommation est atomique. Renouveler les dix codes invalide les anciens. Désactiver la 2FA nécessite le mot de passe et un code TOTP ou de secours valide. Les codes de secours n’ouvrent pas l’historique chiffré.

3. Passkeys et clés de sécurité

WebAuthn est vérifié par SimpleWebAuthn serveur 14.0.3 ; le client 14.0.0 est inclus localement, sans CDN. L’origine et le RP ID sont fixes pour l’installation. L’authentificateur doit vérifier l’utilisateur, avec empreinte, visage ou code/PIN selon ses possibilités. PolyTalk ne reçoit pas les données biométriques.

L’enregistrement exige une confirmation du mot de passe et, si TOTP est activé, un second facteur valide. Les clés doivent être découvrables et assurer la vérification utilisateur : les anciennes clés limitées à la simple présence peuvent être incompatibles. Dix clés maximum par compte. Le retrait empêche les futures connexions avec cette clé ; les sessions qu’elle a déjà ouvertes restent valides.

Les défis durent deux minutes, sont liés à la session d’enrôlement ou au cookie de connexion et ne fonctionnent qu’une fois. La signature, l’origine, le RP ID, le userHandle et le compteur sont vérifiés. Une passkey ne restaure pas automatiquement les clés de messages ni le coffre local. L’identité locale sans mot de passe et le déverrouillage du coffre par biométrie ne sont pas assimilés à cette connexion par passkey.

4. Frontière réelle d’authentification

Le module Synapse épinglé appelle /internal/auth/check avant une nouvelle connexion. Cet appel est authentifié par le secret de politique et échoue fermé si PolyTalk est indisponible. Un compte sans TOTP reste autorisé ; un compte protégé exige un identifiant de dispositif aléatoire accordé par le serveur, limité à trente secondes et consommé une seule fois.

PolyTalk vérifie la première preuve auprès de Synapse. Pour un compte protégé, le jeton obtenu reste uniquement en mémoire serveur pendant deux minutes ; le navigateur reçoit un défi lié à un cookie HttpOnly, SameSite=Strict et Secure en HTTPS. Le jeton n’est renvoyé qu’après la deuxième preuve. Une annulation, une expiration ou cinq essais incorrects entraînent la fermeture de la session temporaire.

Les connexions par mot de passe, wallet et passkey passent par le même second facteur lorsque celui-ci est activé. Une connexion brute Matrix qui ne sait pas présenter ce parcours est refusée pour un compte protégé. Les agents de service peuvent conserver un facteur désactivé par choix de leur responsable, ou intégrer le parcours de défi ; un simple champ TOTP ajouté côté interface n’aurait pas suffi.

Les confirmations sensibles utilisent l’authentification interactive Matrix avec une liste vide de dispositifs : aucune suppression ni nouvelle session. La configuration gérée fixe ui_auth.session_timeout à zéro pour empêcher de réutiliser une confirmation récente. Le début d’activation TOTP effectue en plus une connexion de contrôle pour vérifier que le hook Synapse est réellement chargé.

Déverrouillage local par clé d’accès

Une option supplémentaire, propre au navigateur, utilise l’extension WebAuthn PRF pour chiffrer localement la phrase du coffre. Elle ne change ni la phrase d’origine ni les clés du SDK Matrix. L’utilisateur confirme la phrase actuelle et choisit une passkey déjà associée ; si PRF n’est pas pris en charge, aucune protection de remplacement en clair n’est enregistrée.

Au retour sur cet appareil, le bouton facultatif « Déverrouiller avec ma clé d’accès » demande une vérification utilisateur à l’authentificateur. Sa sortie PRF ouvre une enveloppe AES-GCM liée au coffre et à l’origine ; cette enveloppe contient la phrase nécessaire au stockage cryptographique existant. La sortie PRF et la phrase ne sont pas envoyées au serveur par ce parcours. Conserver la phrase de secours demeure nécessaire si la clé est perdue ou supprimée.

L’activation et la désactivation sont explicites. La fermeture pendant la préparation annule la cérémonie avant une invite tardive. Les contrôles de génération empêchent un déchiffrement ou un scellement tardif de rouvrir la session après verrouillage. Les tests utilisent une sortie PRF simulée et le vrai chiffrement ; le matériel réel reste à qualifier. Cette option ne constitue pas une inscription sans mot de passe au compte.

5. Audit et minimisation des secrets

Activation/désactivation TOTP, renouvellement des secours et ajout/retrait de passkey produisent un événement transactionnel sans code, clé ni mot de passe. L’identité de l’acteur y est pseudonymisée par HMAC. Le nettoyage retire les événements de plus de quatre-vingt-dix jours lors des écritures d’audit. L’utilisateur peut consulter ses cent derniers événements dans les paramètres de sécurité.

Les mots de passe, codes saisis et QR de configuration sont retirés du dialogue fermé. Une validation tardive après fermeture ne doit pas rouvrir une session ou une vue privée. Les jetons en attente ne sont pas enregistrés en clair dans SQLite. Un redémarrage met fin aux défis en mémoire ; une session temporaire côté Synapse peut néanmoins survivre si le processus est brutalement arrêté avant son nettoyage.

6. Vérification et limites

Tests de signatures P-256 et des routes HTTP : enregistrement, origine falsifiée, vérification utilisateur absente, défi ou cookie incorrect, rejeu et retrait. TOTP : vecteurs RFC, chiffrement, premier code, anti-rejeu, consommation des secours, grants, audit et fermeture de dialogue. Module Python : dix-neuf tests dans le conteneur Synapse réel.

Qualification Matrix complète passée : 1/1 en 674,64 secondes sous les quotas stricts conservés. Elle prouve le refus des connexions brutes directe et proxifiée lorsque TOTP est activé, le rejet d’un mauvais mot de passe juste après connexion, le défi lié au cookie, les codes à usage unique, la désactivation et le retour à une connexion normale. Les tests HTTP signés couvrent aussi le maintien du défi TOTP après wallet et passkey. Pile intranet sans sortie Internet : 1/1 en 34,27 secondes. Suite Node finale : 146/146 tests. Build local réussi. Deux revues indépendantes ont porté sur l’authentification et le déverrouillage local ; les défauts relevés ont été corrigés avec régressions.

Restent des travaux distincts : identité locale générée sans mot de passe, connecteurs iCloud/Google Drive/WebDAV, rotation sûre de la clé de sauvegarde et gestion complète des sessions. L’« Invite Google » appartient au fournisseur Google ; elle n’est pas simulée par une notification PolyTalk. Les tests physiques des wallets et clés, l’ID WalletConnect réel et les contrôles d’exploitation TLS/restauration/charge restent des conditions de qualification.

7. Glossaire

Passkey
Clé cryptographique d’authentification gérée par un authentificateur.
RP ID
Domaine auquel une clé WebAuthn est rattachée.
UV
Vérification utilisateur par l’authentificateur, distincte d’une simple présence.
TOTP
Code temporaire calculé à partir d’un secret partagé et de l’heure.
UIA
Authentification interactive Matrix pour confirmer une opération sensible.
Grant
Autorisation serveur courte, liée à une identité et utilisable une seule fois.
Code de récupération des messages
Secret d’une sauvegarde de clés ; distinct d’un code de secours 2FA.
