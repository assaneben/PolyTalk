Polytalk — Plan d’implémentation

But : construire une messagerie humains/agents avec E2EE Matrix, identité et partage, contrôle des expéditeurs et réception durable, distribuable sur Internet et intranet.

Architecture : Synapse/PostgreSQL transportent les événements ; Node.js gère le registre et les politiques. Clients et connecteurs gardent les clés ; le module Synapse contrôle les permissions sans lire le contenu.

Stack : Node.js 24, registre SQLite, Synapse/PostgreSQL, matrix-js-sdk 44.0.0, qrcode 1.5.4, esbuild 0.25.12 ; Matrix Rust SDK pour le connecteur agent, version à épingler après contrôle de compilation.

Spec : conception consolidée. Le builder check indépendant n’a relevé aucune question majeure empêchant de préparer ce plan.

Plan soumis à relecture avant poursuite. Du code serveur existait avant l’invocation de Superpowers ; aucun test applicatif n’est encore annoncé passant.

Contraintes globales

  • Français, profils humain/agent, aucun CDN à l’exécution.
  • UUIDv4 permanent ; nom local de 3 à 32 caractères ; MXID immuable au MVP.
  • Clés privées chez les clients ; échec crypto interdit l’envoi ; aucun repli en clair.
  • Blocage prime sur liste blanche. Politique indisponible : refus des nouveaux messages et invitations contrôlés.
  • Dans un groupe, le refus d’un membre local rejette l’événement pour le salon entier.
  • Fédération extérieure désactivée par défaut ; traitement automatique des agents seulement après configuration autorisée.
  • Aucun mot de passe, jeton, clé privée ou corps de conversation dans les logs applicatifs.
  • Les documents restent HTML autonomes ; le code applicatif utilise un build local reproductible et des dépendances embarquées.

Priorités de revue

  1. Contourner la liste blanche par groupe, invitation ou autre client Matrix : tâche 3.
  2. Réutiliser un appareil après perte de clés : tâches 4 et 6.
  3. Notification doublée entraînant une action répétée : tâches 6 et 7.
  4. Carte altérée, QR hostile ou URL arbitraire : tâche 5.
  5. Installation intranet dépendant encore d’Internet : tâche 8.

Tâche 1 — Identité et politiques persistantes

Fichiers : server/store.mjs ; tests/store.test.mjs.

Interfaces produites : Store.ensure(mxid,name,kind) → Profile ; policy(owner) → {mode,rules} ; allowed(owner,sender) → boolean ; receipt(owner,eventId,state) → Receipt. Consommées par tâches 2 et 3.

  1. Tester identité stable après réouverture, séparation des propriétaires, priorité du blocage et monotonie des accusés.
  2. Pour les comportements manquants et défauts, observer l’échec avant correction. Le code déjà écrit ne sera pas qualifié rétroactivement de TDD.
  3. Implémenter : bloqué → false ; inconnu en liste blanche → false ; autorisé en liste blanche → true ; processed suivi de received conserve processed.
  4. node --test tests/store.test.mjs puis npm test : zéro échec.
  5. Journaliser preuves et décisions ; commit local si le dépôt projet est établi.

Tâche 2 — API authentifiée et serveur web

Fichiers : server/app.mjs ; server/index.mjs ; scripts/setup.mjs ; tests/api.test.mjs.

Interfaces : consomme Store ; produit createApp(config) → http.Server, /api/me, /api/contacts, /api/policy, /api/policy/rules, /api/register, /api/receipts et /internal/evaluate. Les API publiques exigent un jeton Matrix vérifié ; la route interne exige un secret séparé.

  1. Écrire les tests : 401 sans session, 403 mauvaise origine, isolation des politiques, 413 corps excessif, 400 schéma invalide, 429 abus.
  2. Le double HTTP ne remplace que Matrix externe ; garder serveur et SQLite réels. Constater les échecs pertinents avant correction.
  3. Corriger la validation et l’authentification ; destination du proxy fixée en configuration, redirections interdites.
  4. node --test tests/api.test.mjs puis suite complète : zéro échec ; ne pas présenter les tests contractuels comme des échanges Matrix.
  5. Documenter routes et erreurs publiques sans révéler de secret.

Tâche 3 — Pile Matrix et politiques Synapse

Fichiers : deploy/compose.yaml ; deploy/synapse/polytalk_policy.py ; scripts/setup.mjs ; tests/test_synapse_policy.py ; tests/matrix.integration.mjs.

Interfaces : callbacks user_may_invite(inviter,invitee,room_id) et check_event_for_spam(event), consommant /internal/evaluate ; produisent autorisation ou refus Synapse sans déchiffrement.

  1. Tests RED : invitation bloquée, événement refusé par un membre local, refus si service de politique indisponible.
  2. Implémenter le module pour la version Synapse épinglée ; profil Polytalk sans salon public ou non chiffré.
  3. Configurer Synapse/PostgreSQL, secrets générés et ports loopback de développement ; ne pas exposer la fédération.
  4. Tester réellement avec comptes Matrix : blocage, liste blanche vide, autorisation, suppression d’autorisation et contournement par client tiers.
  5. python -m unittest discover -s tests -p test_synapse_policy.py et npm run test:matrix. Sans moteur Docker joignable, état bloqué, jamais validé.

Tâche 4 — Client web chiffré

Fichiers : web/index.html ; web/app.js ; web/style.css ; web/matrix-client.js ; scripts/build.mjs ; tests/client-state.test.mjs.

Interfaces : consomme API et Matrix ; produit connect(session,storagePassword), sendText(roomId,body), createConversation(members), réception et opérations de clés sécurisées.

  1. Tests RED des transitions, du refus d’envoi sans crypto et de la reprise du même appareil.
  2. Construire inscription/connexion, salons, invitations, groupes, fichiers chiffrés limités à 10 Mio et réglages de réception.
  3. Initialiser Rust crypto avant tout envoi ; IndexedDB protégé ; un seul client actif sur une même base crypto.
  4. Vérification d’appareils, export/import de clés protégés et erreur explicite si historique indéchiffrable.
  5. npm run build : succès. Vérification navigateur : échange entre deux comptes, rechargement conservant l’appareil, parcours mobile/clavier et absence de clair dans le relais.

Tâche 5 — Contacts et partage

Fichiers : web/contact.js ; web/app.js ; tests/contact.test.mjs.

Interfaces : consomme profils API ; produit parseContact(input,origin) → ContactReference et format polytalk.contact.v1.

  1. Tests RED du parseur : adresse, lien local, JSON altéré, schéma dangereux, champs secrets interdits et longueur excessive.
  2. Implémenter le parseur sans accès réseau automatique vers une origine arbitraire.
  3. Ajouter copie, QR PNG/SVG local, partage système avec repli, carte téléchargeable et import avec prévisualisation.
  4. Tester sans caméra, partage ou presse-papiers ; sélectionner un décodeur local pour l’import d’image. Aucun scan ne modifie les permissions.
  5. node --test tests/contact.test.mjs, suite complète et essai visuel. Ne pas revendiquer une signature personnelle pour une carte seulement attestée par le serveur.

Tâche 6 — Connecteur local durable

Fichiers : agent/Cargo.toml ; agent/src/main.rs ; agent/src/inbox.rs ; agent/tests/delivery.rs.

Interfaces : consomme Matrix et politiques ; produit commandes JSON lignes login, send, listen, read, ack et événements message.available. Clés et appareil persistants.

  1. Tests RED : crash avant accusé, doublon après reprise, état crypto manquant et message refusé par politique.
  2. Épingler le SDK Rust après contrôle de compilation ; stockage local protégé, curseur et journal durables.
  3. Distinguer reçu, signalé et traité ; aucun modèle lancé par défaut.
  4. cargo test --manifest-path agent/Cargo.toml et échange réel avec le web.
  5. Arrêter le connecteur, envoyer un message, relancer : récupérer sans effet applicatif doublé.

Tâche 7 — Accès agents MCP et A2A

Fichiers : agent/adapters/mcp.mjs ; agent/adapters/a2a.mjs ; tests/adapters.test.mjs.

Interfaces : consomme protocole local du connecteur ; produit outils MCP send_message, read_messages, wait_for_message, ack_message et opérations A2A 1.0 effectivement prises en charge.

  1. Tests RED : envoi/refus, corrélation, attente bornée, annulation et opération non supportée.
  2. Implémenter sans commande shell construite depuis un message ; recontrôle des politiques avant remise.
  3. Tester avec un client MCP réel et une conversation A2A ; Agent Card limitée aux capacités prouvées.
  4. Qualifier séparément Claude channels, Codex App Server et Gemini CLI ; sans client/droits disponibles, indiquer non vérifié et fournir la configuration, pas un badge de compatibilité.
  5. node --test tests/adapters.test.mjs et suite complète ; aucun traitement ou coût LLM automatique.

Tâche 8 — Distribution et vérification finale

Fichiers : deploy/compose.internet.yaml ; deploy/compose.intranet.yaml ; scripts/export-offline.mjs ; README.md ; guides d’exploitation et rapport HTML.

  1. Valider les configurations et générer le paquet : images figées, bundle local, dépendances et licences.
  2. Installer depuis ce paquet avec egress Internet coupé ; vérifier inscription, messages, notifications et rattrapage avec DNS et certificats internes.
  3. Exécuter suites Node/Python/Rust, build, intégration Matrix et inspection des logs ; consigner commandes et résultats réels.
  4. Revue indépendante globale ; défauts critiques/importants reproduits par tests RED puis corrigés GREEN.
  5. Livrer sources, démarrage et statut par fonction. Déploiement public seulement avec domaine/TLS et infrastructure réels ; aucune URL publiée inventée.

Choix d’exécution

Sous-agents avec revue par tâche — recommandé : exécution et relecture séparées par livrable, puis revue globale. Plus de contextes de revue, adapté aux frontières de sécurité entre Matrix, politiques et agents.

Exécution dans ce chat : réalisation ici, tests à chaque tâche puis une revue indépendante finale. Moins de contextes, pas de relecture indépendante à chaque tâche.

Pour les workers : utiliser superpowers:subagent-driven-development ou superpowers:executing-plans selon le choix du porteur. Les nouveaux comportements suivent superpowers:test-driven-development ; les déclarations de réussite suivent superpowers:verification-before-completion.

Aucun dépôt Git projet n’était présent au début ; ne pas annoncer de branche ou de commit inexistant. Les skills téléchargés dans .tooling/superpowers restent distincts du produit. Le moteur Docker non joignable est un prérequis de validation à résoudre.

Journal d’exécution : consigner résultats, décisions et limites à côté du plan. Aucun livrable de ce plan n’est marqué achevé à sa création.

Glossaire

RED/GREEN
Test échouant pour un comportement manquant, puis passant après implémentation.
E2EE
Chiffrement de bout en bout entre clients de confiance.
SDK
Bibliothèque d’intégration d’un protocole.
MXID
Identifiant Matrix comprenant une partie locale et un serveur.
MCP / A2A
Accès aux outils et interactions entre agents ; distincts du chiffrement Matrix.
