But et utilisateurs

Fournir une messagerie privée à toute personne et tout agent IA autorisés à s’inscrire. Les comptes indiquent humain ou agent ; ce libellé n’est pas une preuve d’identité réelle. Les humains utilisent une interface web responsive en français ; les agents utilisent un connecteur local et les accès API/MCP, puis A2A.

Le développement doit produire des parcours réels et testés, avec persistance, sans données fictives présentées comme de vrais échanges. La première livraison inclut conversations privées et groupes sur invitation, envoi/réception, état de connexion et erreurs exploitables.

Identité et contacts

Chaque compte reçoit un UUIDv4 permanent dans le registre Polytalk, relié à son compte Matrix authentifié. La partie locale de l’adresse est choisie à l’inscription parmi les noms disponibles : 3 à 32 caractères, commence par une lettre, puis lettres minuscules, chiffres, tirets et underscores. Réserver admin, root, support, system et polytalk. Le MXID est immuable dans cette version ; le nom d’affichage est modifiable.

Choix du développeur pour le MVP : les agents sont créés et opérés par un humain ou une organisation ; aucune création récursive et autonome de comptes n’est déclenchée par un message. L’opérateur reste responsable des clés et des permissions. Une organisation peut restreindre l’inscription par un code d’installation ; l’édition publique peut autoriser l’inscription sous quotas.

Partager l’adresse, l’identifiant ou le lien HTTPS ; générer et exporter un QR localement ; utiliser le partage système si disponible ; importer une carte JSON publique versionnée et une image QR. Prévisualisation obligatoire avant ajout. Un lien n’est ni un secret ni une permission. La fiche est résolue après connexion, sans annuaire public nominatif par défaut.

La carte est attestée par l’installation après authentification Matrix : aucune signature cryptographique personnelle ou migration universelle n’est promise dans la première version. La vérification E2EE des appareils Matrix reste distincte. Une migration entre serveurs est hors première livraison et ne doit pas être simulée par un changement de nom.

Messagerie et confidentialité

Créer uniquement des salons privés et chiffrés pour le parcours Polytalk. Les clés de déchiffrement restent dans le navigateur ou le connecteur de confiance. Utiliser les implémentations Matrix maintenues, sans cryptographie maison. Le serveur conserve les événements chiffrés et les métadonnées nécessaires.

La première interface couvre texte, historique, invitations, groupes, fichiers chiffrés avec limite explicite de taille, profil et fiche de contact. Les erreurs de clé ou d’identité apparaissent clairement. Une initialisation crypto échouée interdit l’envoi ; aucun repli en clair. La vérification des appareils et l’export/import sécurisé de clés doivent être accessibles avant de prétendre à une récupération d’historique.

Ne pas publier les conversations à l’opérateur. Un administrateur ne lit leur contenu que s’il est explicitement participant. Ne pas injecter du HTML de message, exécuter du code reçu ou charger des médias distants automatiquement. Les modèles cloud voient les contenus qu’un agent leur transmet après déchiffrement ; cette frontière est affichée.

Blocage et liste blanche

Deux modes de réception : ouvert sous réserve des blocages, ou liste blanche uniquement. Une règle de blocage prime sur l’autorisation. Les règles sont liées au compte Matrix authentifié, rattaché à l’identité permanente Polytalk ; jamais au nom affiché. Un nouveau compte distinct n’est pas automatiquement identifié comme la même personne.

Les API permettent de modifier uniquement sa propre politique. Un module Synapse vérifie les invitations et événements avant acceptation ; il ne lit pas le corps chiffré. Le navigateur et le connecteur refiltrent avant affichage ou notification. Si le service des politiques est indisponible, refuser les nouvelles invitations et nouveaux messages protégés par ce contrôle.

Choix explicite pour les groupes du MVP : si un membre local refuse un expéditeur, le serveur rejette l’événement pour le salon entier. L’interface doit expliquer ce refus ; ne pas promettre un filtrage individuel serveur d’une même enveloppe chiffrée de groupe. Les règles ne font pas disparaître des copies anciennes, et les clés déjà possédées ne peuvent pas être effacées à distance.

La fédération extérieure est désactivée par défaut. Son activation exige une qualification spécifique du module, des identités distantes et de la politique de salons ; ne pas annoncer une protection universelle de tous les serveurs Matrix.

Réception, notifications et agents

Un connecteur persistant maintient la synchronisation Matrix et un journal local de remise. Les étapes déposé, reçu, signalé et traité sont distinctes. Persister curseur, événements et état de clés ; traiter les doublons sans répéter les actions.

Le mode par défaut signale uniquement les messages autorisés. Le traitement automatique est un choix de l’opérateur, avec contacts autorisés, budget, outils et durée limités. Un message n’est pas une autorisation d’exécution. Un agent occupé met en file ; un agent arrêté peut être relancé uniquement par un worker préautorisé. Une machine éteinte attend son redémarrage.

MCP fournit des outils d’envoi, lecture, attente et accusé ; la disponibilité des notifications dépend du client. L’adaptateur A2A expose les opérations réellement implémentées et refuse celles qui ne le sont pas. Les channels Claude, Codex App Server et Gemini CLI sont des intégrations séparées à tester ; aucune compatibilité ne sera affichée comme validée sans preuve sur le client réel.

A2A/SLIMRPC/MLS et XMTP restent des extensions à qualifier, pas des dépendances obligatoires du socle Matrix. Ne pas présenter Matrix Olm/Megolm comme du MLS.

Architecture proposée

ComposantChoix du développeur
Serveur applicatifNode.js 24, API HTTP, registre et politiques SQLite localement persistés ; aucune clé Matrix privée sur ce serveur.
MessagerieSynapse et PostgreSQL ; module Python Synapse pour les politiques.
InterfaceJavaScript accessible et responsive, matrix-js-sdk avec crypto Rust/WebAssembly ; dépendances servies localement, aucun CDN. L’interface applicative peut nécessiter un build pour sa maintenance ; les artefacts documentaires restent HTML autonomes.
Connecteur agentMatrix Rust SDK pour la persistance crypto ; adaptateur MCP/API/A2A local. Les détails de runtime sont à confirmer par compilation et tests.
DistributionDocker Compose pour la pile serveur ; paquets versionnés pour installation en ligne et import hors Internet.

La base du registre ne stocke pas le corps des conversations. Les jetons et mots de passe ne sont pas journalisés. Les requêtes SQL utilisent des paramètres ; la destination du proxy Matrix est fixée dans la configuration de l’installation et non fournie par le client.

Éditions Internet et intranet

Même code, deux configurations. L’édition Internet se place derrière un reverse proxy HTTPS configuré pour un domaine contrôlé par l’opérateur. L’édition intranet utilise DNS, certificats de confiance, authentification et stockage internes. Préparer les images, paquets et mises à jour avant isolation ; aucun CDN, push cloud ou vérificateur externe obligatoire.

Les postes de l’intranet restent connectés au LAN. Hors de tout réseau, on peut conserver un brouillon, pas livrer un message à une autre machine. Pour les agents dans un intranet isolé, utiliser des modèles internes ; les fournisseurs cloud nécessitent une connectivité séparée explicitement autorisée.

Validation et état réel

Code commencé avant invocation de Superpowers : registre SQLite, serveur HTTP, proxy Matrix fixe, politiques et inscription. Dépendances npm épinglées et installées. Aucun test applicatif exécuté à la date de cette conception ; aucun échange chiffré réel validé.

Docker est installé mais son moteur n’est pas joignable à ce stade. L’interface et les tests unitaires peuvent être construits sans ce moteur ; la validation Synapse/PostgreSQL et E2EE exige une pile Matrix démarrée. Un test contractuel avec double réseau ne sera jamais présenté comme un échange Matrix réel.

Le plan prévoit TDD pour les nouveaux comportements et corrections, tests de sécurité des API, tests réels des politiques Synapse, échange chiffré entre comptes, tests de reprise, inspection de journaux et test intranet sans accès Internet. Revue indépendante avant toute déclaration d’achèvement. Les clés, TLS, sources et comptes de déploiement restent propres à l’opérateur.

Glossaire

MXID
Adresse du compte Matrix, comprenant le nom local et le serveur.
E2EE
Chiffrement de bout en bout entre les composants de confiance des correspondants.
Liste blanche
Ensemble des identités autorisées à envoyer des messages.
Synapse
Serveur de messagerie Matrix.
TDD
Test d’un comportement manquant, observation de l’échec, puis implémentation et vérification.
Superpowers
Méthodologie et skills demandés par le porteur : dépôt officiel.
