1. Inscription et connexion guidées

1 — Votre compte
Identifiant et mot de passe. À l’inscription : nom, aperçu de l’adresse et code d’invitation si nécessaire.

2 — Cet appareil
Phrase locale confirmée, distincte du mot de passe. Elle protège les clés et la session sauvegardées sur cet appareil.

Au retour
Choix du compte enregistré et phrase locale uniquement, sans créer un nouveau jeu de clés.

Les titres, boutons et aides indiquent l’étape active. Les champs masqués ne doivent pas bloquer sa validation. Les mots de passe peuvent être affichés ou masqués explicitement ; ils redeviennent masqués au changement de vue. Les gestionnaires de mots de passe bénéficient des attributs adaptés au compte. Les informations du coffre local ne sont pas transmises dans les demandes d’authentification.

Les contrôles avant envoi vérifient la longueur de la phrase locale, sa confirmation et sa différence avec le mot de passe du compte. Les doubles soumissions sont bloquées pendant le traitement. Si la création du compte a réussi mais que la connexion échoue, une nouvelle tentative ne recrée pas le compte. Un identifiant déjà pris produit une explication et propose de changer d’identifiant ou de se connecter.

Une aide contextuelle distingue mot de passe du compte et phrase locale. Elle explique la récupération disponible auprès de l’administrateur, sans annoncer de récupération automatique par e-mail ni de restauration magique des clés. Les anciennes conversations peuvent nécessiter un appareil déjà vérifié ou une sauvegarde de clés sur un nouvel appareil.

Le lien fourni vers le SDK WalletConnect pour wallets a été étudié. PolyTalk est l’application qui demande l’authentification : l’intégration utilise donc le client d’application Sign Client, et non un moteur de paiement ou un SDK transformant PolyTalk en portefeuille.

La première version accepte une preuve de clé Ethereum EOA par EIP-191. Le connecteur direct utilise le réseau déclaré par le wallet ; WalletConnect propose actuellement la chaîne Ethereum eip155:1 pour cette signature sans transaction. Les wallets de contrats ERC-1271, les réseaux non EVM et l’authentification multichaîne complète ne sont pas annoncés comme pris en charge.

Pour préserver les identifiants choisis et éviter les associations implicites, un wallet doit d’abord être lié à un compte existant depuis Réglages → Mes wallets de connexion. Cette association exige une session valide, le mot de passe du compte et une signature du wallet. Un wallet inconnu ne crée pas automatiquement un compte. L’inscription uniquement par wallet reste une évolution distincte.

3. Protocole et frontières de sécurité

  1. Le serveur génère un message au format SIWE : domaine, origine, adresse, chaîne, nonce aléatoire, date, expiration et identifiant de demande. Le but signé distingue association et connexion.
  2. Un cookie temporaire HttpOnly, SameSite=Strict et Secure en HTTPS lie le défi au navigateur. L’origine exacte est exigée pour les modifications.
  3. Le wallet signe uniquement par personal_sign. PolyTalk ne demande ni transfert, ni autorisation de dépense, ni transaction.
  4. Le serveur vérifie le message qu’il a lui-même conservé et récupère l’adresse signataire avec ethers 6.17.0. Une modification du message, du navigateur, du but ou de l’origine échoue. Le défi expire en cinq minutes et n’est utilisable qu’une fois.
  5. Pour un wallet déjà associé, le serveur émet un JWT interne de 60 secondes vers Synapse. L’algorithme HS256, l’émetteur et l’audience sont fixes. Le JWT ne revient jamais au navigateur ; celui-ci reçoit une session Matrix normale du compte lié.
  6. Le coffre local reste nécessaire sur le nouvel appareil. La signature et la clé privée du wallet ne servent jamais à dériver les clés des conversations.

Les associations sont uniques par adresse, limitées à cinq wallets par compte. Ajouter ou retirer une association nécessite une confirmation du mot de passe. Retirer un wallet empêche les futures connexions par cette adresse, mais ne ferme pas les sessions Matrix déjà ouvertes. Les mots de passe, signatures, JWT et URI d’appairage ne sont pas journalisés par le code de PolyTalk. Les défis expirés sont nettoyés au démarrage et lors des nouvelles demandes.

Les règles de réception, les identifiants UUID et les autorisations opérateur restent ceux du compte Matrix. Une connexion wallet ne confère aucun droit supplémentaire. La clé JWT du serveur est un secret d’authentification sensible : elle reste dans la configuration privée et n’est pas transmise aux connecteurs natifs.

WalletConnect n’est initialisé qu’après sélection explicite. La session ne demande que personal_sign, garde son stockage en mémoire, désactive sa télémétrie configurée et ferme l’appairage à la fin. Les messages de chat, phrases locales et secrets de compte ne lui sont pas transmis. Le relais reste un service tiers avec ses propres métadonnées de connexion. Son accès réseau est limité par la politique CSP lorsqu’un Project ID est configuré.

4. Configuration et fonctionnement intranet

Exécuter la préparation locale pour ajouter une clé dédiée sans rotation des secrets existants, puis redémarrer Synapse et PolyTalk :

npm run setup
docker compose --env-file .env -f deploy/compose.yaml restart synapse
npm start

La préparation ajoute MATRIX_JWT_SECRET et configure le login JWT de Synapse avec émetteur et audience correspondant à PUBLIC_ORIGIN. Ne jamais publier .env. Pour activer le QR WalletConnect, créer un projet propre à PolyTalk dans le tableau de bord WalletConnect/Reown, autoriser les origines de l’application et configurer :

WALLETCONNECT_PROJECT_ID=identifiant-du-projet-reel

Le Project ID est un identifiant public de service, pas une clé privée de wallet. Il doit provenir du projet réel ; aucune valeur de démonstration n’active le relais. Aucun compte tiers ni projet n’a été créé par l’agent de développement.

La vérification cryptographique EOA de PolyTalk n’utilise pas de RPC blockchain. Le wallet choisi peut toutefois dépendre de ses propres services réseau. WalletConnect exige son relais Internet : il ne remplace pas l’accès local en intranet isolé. La connexion par compte et coffre reste disponible, avec HTTPS et certificat approuvé par les appareils hors localhost.

Routes : POST /api/wallet/challenge, /login, /link et /unlink ; GET /api/wallet/list. Les preuves sont liées à une origine et un navigateur ; aucun jeton secret n’est placé dans les URL. Les tentatives sont bornées par des quotas distincts pour défis et validations.

5. Qualification

La suite Node comporte 105 tests réussis et vérifie les erreurs de phrase locale, les reprises après inscription partiellement terminée, l’anti-rejeu, l’origine, le navigateur, l’expiration, l’association avec confirmation du mot de passe, le JWT Matrix et les changements de compte du fournisseur. Les tests du connecteur WalletConnect vérifient une session de signature seule et sa fermeture avec un transport simulé.

Test réel réussi : 1 scénario en 1,44 seconde sur Synapse local : compte existant, signature EOA cryptographique, association, nouvelle session Matrix de même identité, refus du rejeu, retrait de l’association et déconnexion. Le signataire est un wallet de test créé en mémoire ; cela ne constitue pas un essai matériel Ledger, une session MetaMask réelle ou un test du relais WalletConnect.

Le build conserve les ressources locales versionnées et publie le HTML après leurs écritures. Le SDK WalletConnect est dans un module différé : il n’est pas inclus dans le code d’entrée chargé pour tous les utilisateurs. Un test vérifie cette séparation et le chargement du module à la demande.

6. Code d’invitation facultatif

Mise à jour : inscription ouverte par défaut, sans code et sans champ affiché. Le mode sur invitation est un choix explicite de l’administrateur. La commande setup avec --signup-mode open désactive cette restriction ; --signup-mode invitation l’active. Une relance sans cette option conserve le mode existant. Redémarrer le service applicatif après modification.

Le champ explique qu’il autorise la création du compte sur cette installation. L’utilisateur doit l’obtenir de la personne qui l’invite ou de l’administrateur de son organisation. Il est distingué du mot de passe du compte et de la phrase locale du coffre.

Une aide dédiée précise que le code n’est pas nécessaire pour se connecter à un compte existant. Une rubrique administrateur indique le paramètre SIGNUP_CODE du fichier privé .env, sans afficher la valeur du code aux visiteurs. Le champ permet de vérifier visuellement le collage avec Afficher/Masquer et le message de refus indique comment corriger le problème.

9. Glossaire

SIWE
Message standard d’authentification Ethereum, distinct d’une transaction.
EOA
Compte Ethereum contrôlé par une clé de signature ; distinct d’un wallet de contrat.
Nonce
Valeur aléatoire qui empêche de rejouer une authentification.
JWT
Preuve signée interne permettant au serveur d’ouvrir la session Matrix vérifiée.
Coffre local
Stockage chiffré propre à l’appareil, protégeant session et clés des conversations.
Project ID
Identifiant du projet WalletConnect/Reown nécessaire pour utiliser son relais.
Appairage
Connexion temporaire entre l’application et le wallet ; son QR contient un secret et doit rester privé.
