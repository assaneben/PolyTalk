Exigences confirmées

Chaque agent doit pouvoir savoir qu’il a reçu un message. Un agent actif reçoit un événement ; un agent déconnecté retrouve les messages conservés à son retour. Le produit doit disposer d’une édition en ligne et d’une édition intranet utilisable sans Internet.

Le réveil automatique est optionnel, limité à un runtime autorisé par le propriétaire. Aucun simple message ne donne le droit de lancer une commande ou de modifier un projet. Le choix du socle recommandé est détaillé dans l’étude comparative.

Préférer une connexion sortante du poste vers le serveur : aucun port public à ouvrir sur chaque poste. Les échanges entre daemon et adaptateurs utilisent IPC ou interface locale authentifiée, sans exposition générale du contenu en clair.

États observables et signification

  1. Déposé : le serveur a accepté l’événement.
  2. Synchronisé : le daemon l’a enregistré localement de manière durable.
  3. Déchiffré et vérifié : clés, identité et schéma ont passé les contrôles.
  4. Signalé : l’adaptateur a accepté l’avis de disponibilité.
  5. Remis au runtime : le client a confirmé son admission ; ce n’est pas une preuve de compréhension du modèle.
  6. Traitement terminé : résultat applicatif explicite, si un traitement a été autorisé.

États d’exception : clés manquantes, destinataire non autorisé, agent indisponible, traitement refusé ou expiré. Une alerte perdue ne supprime jamais le message durable. Un accusé Matrix de lecture ne remplace pas un accusé de traitement Polytalk.

Reprise, rediffusion et contrôle des doublons

Conception Polytalk : transaction locale enregistrant l’événement, son identifiant et le travail de notification avant d’avancer le curseur durable. Le daemon accuse réception du signal séparément de son traitement. En cas de crash, reprendre les travaux non terminés ; dédupliquer par identité de destinataire et identifiant de message.

Un historique de synchronisation limité exige de combler les trous selon l’API et la rétention disponible. La présence du message sur le serveur ne garantit pas que le client dispose encore des clés : restaurer l’état cryptographique ou signaler le problème. Ne pas réinitialiser une identité à chaque redémarrage.

Prévoir retries bornés, temporisation progressive, file d’échecs et relecture contrôlée. Pour des actions externes, propager une clé d’idempotence lorsque le service le permet. Sinon, signaler une exécution ambiguë après crash au lieu de promettre « exactement une fois ».

Réveil autorisé et agent occupé

Trois modes : notification seule ; traitement automatique de contacts et tâches autorisés ; validation humaine avant traitement. Le défaut proposé est la notification seule. Un lanceur local configuré peut démarrer un worker ou une session gérée avec identité, budget, durée et outils limités.

Si l’agent est occupé, mettre les messages en file ; ne pas interrompre son tour par défaut. L’injection dans un tour actif n’est permise que si l’intégration et la politique le prévoient. Empêcher les boucles entre agents : ne pas répondre aux accusés, conserver corrélation et causalité, limiter échanges et coûts.

Une machine éteinte ne reçoit aucun événement local. Le serveur conserve les messages suivant sa rétention ; la reprise attend le redémarrage. Le wake-on-LAN ou le pilotage de postes est hors MVP et demanderait une autorisation et une étude séparées.

Les éditions partagent le protocole et les fonctionnalités de base ; elles ne synchronisent pas automatiquement entre elles à travers une isolation réseau. Tout transfert entre domaines doit faire l’objet d’un besoin explicite et d’une conception dédiée.

Plan de validation indispensable

  • Message en ligne : mesurer séparément dépôt, synchronisation et remise au runtime ; définir un objectif de latence après mesure.
  • Agent arrêté, puis lancé ; daemon arrêté ; serveur redémarré ; poste éteint : vérifier la reprise, sans perte silencieuse ni action doublée.
  • Rupture réseau et historique tronqué : pagination et rattrapage corrects.
  • Clé manquante ou appareil non vérifié : état d’erreur explicite et aucune remise en clair à un relais.
  • Agent occupé : file respectée ; aucun mélange de conversations.
  • Webhook rejoué, identité révoquée, message hostile et boucle de réponses : refus ou limites vérifiables.
  • Intranet isolé : couper DNS Internet et egress ; vérifier installation depuis paquet local, authentification, échange et notification sans APNs/FCM/CDN ni modèle cloud.
  • Tester séparément Claude Code, Codex et Gemini CLI sur les versions et droits annoncés.

Tous ces tests restent à exécuter. Le système n’a pas encore été implémenté.

Glossaire

API
Interface d’accès programmatique aux fonctions de Polytalk.
MCP
Model Context Protocol : accès d’un agent à des outils et ressources.
A2A
Agent2Agent : protocole d’interaction entre agents indépendants.
SLIM
Secure Low-Latency Interactive Messaging : infrastructure de transport et de sessions.
SLIMRPC
Binding RPC sur SLIM ; l’intégration A2A correspondante reste expérimentale.
MLS
Messaging Layer Security : protocole de chiffrement de groupe utilisable aussi pour deux clients.
Binding
Association des opérations d’un protocole à un transport et à une représentation sur le réseau.
Protobuf
Format de sérialisation structuré utilisé par le binding SLIMRPC.
AAD
Additional Authenticated Data : données liées cryptographiquement au message mais non chiffrées.
Epoch
Version de l’état cryptographique d’un groupe MLS.
KeyPackage
Matériel public signé destiné à l’ajout d’un client MLS ; aucune clé privée ne doit être publiée.
Agent Card
Description des capacités et interfaces d’un agent ; distincte de la carte de contact cryptographique Polytalk.
Composant local de confiance
Processus sous le contrôle du propriétaire de l’agent, chargé des clés et du chiffrement.
PoC
Prototype destiné à vérifier la faisabilité ; il ne prouve pas à lui seul l’aptitude à la production.
ADR
Décision d’architecture datée, motivée et accompagnée de conséquences.
TLS / mTLS
Protection des connexions réseau ; mTLS ajoute l’authentification mutuelle. Ces connexions ne remplacent pas MLS.
Matrix
Protocole de messagerie et synchronisation fédérée.
Element
Clients et solutions autour de Matrix ; ni le protocole ni le moteur d’un agent.
Synapse
Implémentation de serveur Matrix auto-hébergeable.
XMTP
Infrastructure de messagerie avec identités cryptographiques et chiffrement MLS.
Daemon local
Processus persistant autorisé, près de l’agent, qui synchronise et signale les messages.
Hors ligne intranet
Serveur et clients connectés au réseau local, sans dépendance à Internet ; distinct d’un ordinateur sans aucune connexion réseau.
Curseur
Repère de synchronisation persisté pour reprendre la lecture des événements.
Idempotence
Gestion permettant de recevoir plusieurs fois un événement sans répéter son effet applicatif.
