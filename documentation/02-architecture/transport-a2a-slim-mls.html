Statut actuel de cette architecture

Actualisation du 16 octobre 2026 : Matrix devient le socle recommandé du MVP après ajout des besoins de boîte aux lettres, réception événementielle et éditions Internet/intranet autonome. La cible SLIMRPC/MLS ci-dessous reste une option spécialisée à qualifier ; elle n’est plus le transport unique du produit. Voir l’étude des deux meilleures combinaisons.

Décision retenue pour le dossier

Cible recommandée : A2A → SLIMRPC → session SLIM avec MLS activé → relais SLIM. Le destinataire réalise le chemin inverse dans son environnement de confiance. Réutiliser le binding existant plutôt que créer un encapsulage cryptographique propriétaire.

Statut : choix de conception retenu pour le prototype ; mise en production conditionnée aux preuves de validation. Aucune application de messagerie n’est implémentée dans ce dossier. L’expression « meilleure solution » désigne ici le meilleur compromis identifié pour les besoins exprimés, pas un classement de sécurité absolu.

L’intégration A2A/SLIMRPC est expérimentale et n’appartient pas au cœur A2A. [Source : SLIM — intégration A2A]

Intégration progressive

API et MCP, puis A2A, puis validation de SLIM et MLS. La validation précoce de la frontière de confiance commence à l’étape 1 ; la qualification du couple SLIM/MLS constitue l’étape 3. Cet ordre ne permet pas de lancer une messagerie privée sans E2EE.

Tant que le profil E2EE n’est pas validé : démonstration sur données synthétiques uniquement.

SLIMRPC → A2A
  1. Résoudre le contact et vérifier le lien entre identité Polytalk, identité du client MLS et interface annoncée. Le routage vers une instance ne constitue pas cette preuve.
  2. Choisir une version A2A publiée et figer un ensemble compatible : schéma a2a.proto, adaptateur, SLIMRPC et SDK SLIM. Départ proposé : A2A 1.0.0 ; ne pas mélanger les opérations d’une version future avec ce profil.
  3. Sérialiser les requêtes, réponses et événements A2A en Protobuf via le binding SLIMRPC. Déclarer l’interface expérimentale dans supportedInterfaces, avec le protocolBinding publié et l’adresse SLIM attendue par la révision épinglée.
  4. Établir la session entre composants de confiance des agents ; exiger MLS. Le relais transporte les messages de session et les charges chiffrées ; il n’est pas membre du groupe MLS.
  5. Chez le destinataire : vérifier la session et l’identité, déchiffrer, valider le schéma et l’autorisation, puis remettre le message à l’agent. Les réponses suivent la même protection.

Le binding réutilise les types Protobuf d’A2A et prévoit les paramètres de service dans une carte de métadonnées. [Source : A2A — binding SLIMRPC expérimental, spécification v1]

Intégrité du routage et négociation des capacités

Politique de conception : lier au message le contexte immuable de destination et la version du profil. Si le SDK expose l’AAD MLS, y encoder seulement les identifiants opaques nécessaires, avec une représentation déterministe et versionnée. Sinon, conserver ces valeurs dans le contenu protégé et les comparer au contexte de session après déchiffrement. Le choix exact doit être figé et testé, sans modifier les primitives MLS.

Ne pas authentifier comme données immuables les éléments modifiés légitimement en transit, comme un compteur de sauts. Une expiration extérieure peut limiter la file du relais ; si sa valeur a un effet applicatif, une expiration authentifiée dans le contenu doit aussi être vérifiée par le destinataire. Une modification de destination doit échouer ou être rejetée, jamais conduire à une exécution silencieuse.

Exiger un profil de sécurité commun. En l’absence de MLS ou de capacité nécessaire, refuser le mode privé ; aucune conversion centrale vers du clair. TLS reste obligatoire sur les liens pour protéger les échanges réseau. [Source : IETF — RFC 9750, architecture MLS]

Identités, clés et autorisations

L’identifiant stable Polytalk est distinct des clés et des noms d’instance SLIM. Le composant local vérifie les correspondances avec les identités autorisées ; un annuaire ne doit pas suffire à imposer une nouvelle clé sans contrôle. Une rotation conserve l’adresse publique, mais exige une continuité vérifiée ou une procédure de récupération explicite.

Pour le PoC : identités distinctes par agent, vérification stricte du pair et liaison identité/nom activée en mode bloquant lorsque disponible. Écarter les secrets symétriques partagés entre agents indépendants. L’authentification de connexion et l’identité applicative sont des contrôles séparés. [Source : SLIM — authentification]

Les autorisations restent nécessaires pour chaque conversation et chaque action. Une signature valide ne rend pas une instruction reçue autorisée. En cas de révocation : couper les accès au service, retirer le client du groupe et finaliser la transition cryptographique ; l’expiration d’un jeton seule ne révoque pas les secrets de groupe déjà détenus.

Sessions, groupes et absence de service central déchiffrant

Commencer par deux agents identifiés et une session MLS explicitement activée ; tester ensuite les groupes. [Source : SLIM — sessions point à point]

Le modérateur de groupe doit être un composant de confiance désigné par le propriétaire ou les membres. Un Channel Manager central participant au groupe pourrait étendre la frontière de confiance : ne pas lui attribuer ce rôle pour les conversations privées sans vérification. Les relais restent hors des membres autorisés.

Les sessions SLIM ont leurs propres règles de présence, de groupe et de reprise. [Source : SLIM — sessions de groupe] Ne pas assimiler leur fiabilité en ligne à une boîte aux lettres durable. MLS assure des fonctions cryptographiques ; les règles d’adhésion, de stockage et de livraison relèvent aussi de l’application.

Livraison différée, reprises et limites

Concevoir une file persistante contenant uniquement les enveloppes chiffrées, avec durée de conservation, quotas et accusé de dépôt. Un accusé de dépôt ne vaut ni déchiffrement réussi ni traitement par l’agent. L’accusé applicatif doit revenir dans le canal protégé.

Le PoC doit établir si le SDK sait délivrer à un agent hors ligne avec l’état cryptographique disponible. Si non, annoncer « session en ligne » uniquement et différer la fonction boîte aux lettres ; ne pas retirer puis réinviter un destinataire en prétendant qu’il pourra lire l’historique manqué.

Gérer doublons, ordre des événements, restauration après panne et reprise des états MLS avant de promettre une livraison différée. L’idempotence applicative doit empêcher qu’un message retransmis déclenche deux actions ; aucune garantie « exactement une fois » n’est annoncée.

Faits vérifiés, décisions et inconnues

Vérifié dans les sources : binding A2A/SLIMRPC existant et expérimental ; support MLS optionnel dans SLIM ; routage sans lecture de la charge utile ; champs MLS non chiffrés. SLIM reste décrit par un Internet-Draft individuel, pas par une norme IETF adoptée. [Source : SLIM — Internet-Draft individuel, révision 02]

Décidé pour Polytalk : progression API/MCP → A2A → validation SLIM/MLS ; E2EE obligatoire pour le mode privé ; composants cryptographiques chez les agents ; enveloppe extérieure minimale ; absence de repli silencieux.

À prouver : compatibilité des versions et des clients, protection exacte des métadonnées SLIMRPC, fonctionnement des clés et identités dans les SDK, reprise hors ligne, sécurité du modérateur et performances.

Écarts documentaires à résoudre : le draft SLIM décrit un adressage de méthode dans le nom de service, tandis que la documentation actuelle SLIMRPC place service et méthode dans les métadonnées. Les explications de l’authentification réseau dans le binding et de l’identité applicative dans le SDK ne sont pas identiques. Il faut donc épingler les révisions et vérifier le code réellement utilisé ; ne pas fusionner les exemples de plusieurs générations.

Glossaire

API
Interface d’accès programmatique aux fonctions de Polytalk.
MCP
Model Context Protocol : accès d’un agent à des outils et ressources.
A2A
Agent2Agent : protocole d’interaction entre agents indépendants.
SLIM
Secure Low-Latency Interactive Messaging : infrastructure de transport et de sessions.
SLIMRPC
Binding RPC sur SLIM ; l’intégration A2A correspondante reste expérimentale.
MLS
Messaging Layer Security : protocole de chiffrement de groupe utilisable aussi pour deux clients.
Binding
Association des opérations d’un protocole à un transport et à une représentation sur le réseau.
Protobuf
Format de sérialisation structuré utilisé par le binding SLIMRPC.
AAD
Additional Authenticated Data : données liées cryptographiquement au message mais non chiffrées.
Epoch
Version de l’état cryptographique d’un groupe MLS.
KeyPackage
Matériel public signé destiné à l’ajout d’un client MLS ; aucune clé privée ne doit être publiée.
Agent Card
Description des capacités et interfaces d’un agent ; distincte de la carte de contact cryptographique Polytalk.
Composant local de confiance
Processus sous le contrôle du propriétaire de l’agent, chargé des clés et du chiffrement.
PoC
Prototype destiné à vérifier la faisabilité ; il ne prouve pas à lui seul l’aptitude à la production.
ADR
Décision d’architecture datée, motivée et accompagnée de conséquences.
TLS / mTLS
Protection des connexions réseau ; mTLS ajoute l’authentification mutuelle. Ces connexions ne remplacent pas MLS.
